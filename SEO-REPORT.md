# Portfolio SEO implementation report

Site: https://soumitrasamanta69.netlify.app/

Audit and implementation date: 16 October 2026

The project is a Next.js 16 App Router application with a separate CMS/API backend.
The public website has one indexable page. About, Skills, Services, Projects and
Contact are homepage anchors; `/admin` is a separate, non-indexable application.
The existing dark/light presentation, nine top-level sections, CMS controls,
gallery, 3D fallback and message/inquiry workflows are retained.

- Metadata and routes: `frontend/app/layout.js`, `page.js`, `robots.js`,
  `sitemap.js`, `not-found.js`; `frontend/next.config.mjs`.
- Public content and images: `frontend/shared/seo-content.mjs`,
  `image-assets.mjs`, `image-assets.json`, `offline-content.json`;
  `frontend/services/content-source.mjs`.
- Components: `PublicPortfolio.js`, `ServiceOverview.js`, `Projects.js`,
  `ProfilePhoto.js`, `Gallery.js`, `HeroScene.js`; `frontend/app/portfolio.css`.
- Assets: three WebP project screenshots, one WebP portrait, branded social
  preview SVG/PNG, `favicon.svg` and `apple-touch-icon.png` under `frontend/public`.
- Tooling/docs: `scripts/optimize-images.mjs`, `scripts/create-seo-assets.mjs`,
  `package.json`, `frontend/.env.local.example`, `README.md`, this report.
- Verification: `tests/unit/seo.test.mjs`, `tests/e2e/seo.spec.cjs`; existing
  design, portfolio, outage and CMS browser assertions adapted to the new H1 and
  the distinction between public service areas and hidden contact information.

## 6. Structured data

Server-rendered, safely serialized JSON-LD contains a connected **Person**,
**WebSite** and **WebPage** graph. Person references the actual visible CMS social
profiles; hidden profiles and hidden photos are omitted. Optimized local profile
images are used when available. JSON parsing, graph references and script-tag
injection handling are covered by tests.

There is no factual business address, business registration, review or rating
evidence, so no LocalBusiness/ProfessionalService or review markup was added.
BreadcrumbList was also omitted: this one-page portfolio has no genuine nested
page hierarchy. Its anchor links are not separate pages. These schema types do
not imply eligibility for a Google rich result; use Schema.org's validator for
general schema checks and Google's Rich Results Test for supported features.

## 7. Sitemap status

`/sitemap.xml` is generated by the native Next.js metadata route. It contains
exactly `https://soumitrasamanta69.netlify.app/`, with no invented last-modified
date. Admin/API URLs, query variants and homepage anchors are excluded.
Before these changes, the live sitemap returned 404. Redeployment is needed to
make the new route available publicly.

## 8. Robots.txt status

`/robots.txt` allows public crawling, including CSS, JavaScript, public images and
public `/api/media/` image URLs. Administrative and submission API paths are
excluded. The sitemap URL is declared. `/admin` remains crawlable so its existing
noindex metadata can be observed; an additional `X-Robots-Tag: noindex, nofollow`
header reinforces that instruction. Authentication still protects admin APIs;
robots.txt is not an access-control mechanism.

Before these changes, the live robots file returned 404. The new route requires
redeployment.

## 9. Canonical URL

The homepage emits one canonical:
**https://soumitrasamanta69.netlify.app/**

Next.js serializes root-origin metadata without the final slash; this normalizes
to the same homepage URL, rather than a second page or a different canonical.

The canonical, sitemap, social URL and structured-data identifiers share the
production `SITE_URL` constant. This intentionally takes precedence over the old
CMS canonical field to prevent invalid or inconsistent canonical targets. Update
that constant when intentionally moving to a new production domain.

Open Graph title, description, URL, type, site name, locale and absolute image URL

## 11. Image SEO

Public project and profile images have meaningful alt text and intrinsic width/
height. Project/gallery/service images use lazy loading; the small visible hero
portrait uses eager loading. Responsive `sizes` hints remain in place. Known
original asset paths map to descriptive WebP filenames, preserving existing CMS
records and original file URLs. Uploaded and remote images retain their existing
access behavior; no private upload is routed through a public optimization cache.

## 12. Technical SEO

The public page and editorial copy remain server-rendered, including during an
API outage. Metadata/page content share the existing cached-per-request content
loader. No fabricated `/about`, `/services` or location pages were created.
Project links have descriptive visible text and the six existing demo/source
URLs returned HTTP 200 during this audit. A branded not-found view provides
useful return links while unmatched routes retain HTTP 404 and noindex behavior.
Theme switching, reduced motion, keyboard controls, labels, contact validation,
CMS privacy and responsive behavior remain part of browser verification.

## 13. Performance improvements

The four original local images total **11,988,944 bytes**. Their WebP replacements
total **261,002 bytes**, a **97.8% reduction in source-asset size**. The largest
original was a 7.65 MB portrait; its replacement is 42,844 bytes. Actual browser
transfer also depends on Next.js image sizing, format negotiation and caching;
this is not a claim of a 97.8% faster page.

Explicit dimensions and responsive image sizing reduce avoidable layout changes.
The existing on-demand Three.js renderer remains paused offscreen and disabled
for unsupported/mobile/reduced-motion conditions; data-saving connections now
also keep the CSS fallback. No SEO animation library, font provider or tracking
script was added. No PageSpeed score or field LCP/CLS/INP improvement is claimed
without deployed measurements.

## 15. Exact manual Google Search Console steps

1. Deploy these changes to the existing Netlify production site. Open the HTTPS
   homepage, `/robots.txt` and `/sitemap.xml` and confirm each returns 200. Open an
   invented URL and confirm 404. Check that the homepage has no noindex header or
   meta tag.
2. Sign in at https://search.google.com/search-console/ with your own Google
   account. Select **Add property → URL prefix**. Enter exactly
   `https://soumitrasamanta69.netlify.app/`. URL-prefix verification is suitable
   for this Netlify subdomain; a DNS Domain property would require DNS ownership.
3. Choose **HTML tag** verification. Copy only the token from the provided
   `content="..."` value. In Netlify's environment variables, set
   `GOOGLE_SITE_VERIFICATION` to that token for production. Rebuild and redeploy.
   Confirm the homepage source contains the issued `google-site-verification`
   meta tag, then return to Search Console and click **Verify**. Keep the token
   in place after verification. No token or Google login was fabricated.
4. In **Sitemaps**, enter `sitemap.xml` and click **Submit**. Check the processed
   sitemap result after Google retrieves it; fix any reported fetch/parsing issue.
5. Use **URL inspection** on the exact homepage URL. Select **Test live URL** and
   review availability, crawl/indexing permission and the rendered page. Confirm
   the user-declared canonical is the HTTPS URL above. Once the live test is
   successful, click **Request indexing** if offered. This does not guarantee
   indexing or a ranking.
6. Review **Page indexing**, **HTTPS**, **Core Web Vitals**, **Manual actions** and
   **Security issues** as reports become available. Use the **Performance** report
   to assess actual queries, impressions, clicks and geographic relevance over
   time. Keep sitemap and canonical URLs aligned if the production domain changes.

For Bing, verify the same real site in Bing Webmaster Tools (or use its supported
Search Console import) and submit the same sitemap. The optional
`BING_SITE_VERIFICATION` variable supports the issued `msvalidate.01` token.

No webmaster property was created, verified or submitted automatically.
